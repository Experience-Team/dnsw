Changing a token value

  1. Change it in the code: shared.css for the base, or the brand's theme file.
  2. Keep the comment beside it up to date. It is the description shown on these pages.
  3. Check the colour page for contrast in every brand: text roles need 4.5:1, large text and controls 3:1.
  4. Add a line to the changelog.

Adding a token

Ask first whether an existing role covers it. If it does not, add the role to :root in shared.css with a comment saying what it is for, then set it in every brand that needs a different value. Name it by job, not by look (--c-line-strong, not --c-grey-9e).

Documenting a component

  1. Add the page to nav.js and write it in pages/components/.
  2. Cover: when to use it and when not, anatomy, states (live), behaviour, accessibility, content, and the tokens and classes it uses.
  3. Add a live example (see for developers).
  4. Mark it Documented in the inventory.

Moving a project module into core

When a second project needs it:

  1. Remove anything project-specific from its CSS: hard-coded values become tokens, project wording becomes content passed in.
  2. Check it in every brand with the brand switch.
  3. Rename its classes only if both projects can move at once; otherwise keep the old class as an alias until they can.

Behaviour rules

The interaction rules come from things reviewers had to point out. A new lesson is worded as a general principle (not the one case), fitted into the existing list, and agreed before it is added. The same lessons live in the repository's CLAUDE.md, which is where the build checks them.
